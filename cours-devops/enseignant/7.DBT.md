# Guide enseignant · Chapitre 7 · Industrialiser les transformations avec dbt
[← Support étudiant](../7.DBT.md)

## En bref

- **Durée :** 4h, en **2 séances de 2h**. Séance 1 : pourquoi dbt, médaillon, création du projet, seeds, premiers modèles (silver + un modèle gold). Séance 2 : modèles gold, tests (dont le « saboteur »), documentation, flux PR, tableau de bord gold, mission finale, lancement des projets d'évaluation.
- **Prérequis matériel :** chaque étudiant a son dépôt `datacafe-streamlit` (chapitres 5 et 6) avec l'environnement virtuel `stenv`, le `.gitignore` contenant `stenv/` et `*.duckdb`, et le CLI `duckdb` du chapitre 6. **dbt doit être installé avant la séance 1** (section « 💻 À préparer avant la séance » du support) : l'annoncer à la fin du chapitre 6 et relancer par message 48h avant.
- **À préparer avant :**
  - faire tourner soi-même tout le chapitre sur une machine propre, avec la version de dbt que les étudiants auront (voir « À vérifier avant la séance » ci-dessous) ;
  - préparer un **dépôt ou une branche de secours** `pipeline-dbt-correction` contenant tous les fichiers finaux (`dbt_project.yml`, `profiles.yml`, les 2 seeds, les 4 modèles, `silver.yml`, `gold.yml`, `seeds.yml`, le test singulier, `dashboard_gold.py`) : un étudiant en retard copie les fichiers et rattrape le groupe en 2 minutes ;
  - avoir les fichiers `seeds/ventes_brutes.csv` et `seeds/regions.csv` faciles à copier (le support les contient) ;
  - pour la fin de la séance 2 : la liste des **équipes de 4**, le choix du projet d'évaluation par équipe, l'attribution des jeux de données et les **dates de rendu** (voir « Lancer les projets d'évaluation »).
- **Fil DataCafé :** l'export du week-end contient un doublon, une ville `paris` et une quantité manquante, les chiffres présentés au directeur étaient faux ; on construit une chaîne de fabrication bronze/silver/gold testée, comme pour le café.
- **Les 3 messages clés :**
  1. **dbt ne stocke rien** : il orchestre des `SELECT` dans le bon ordre grâce à `ref()`. DuckDB fait le travail et garde les tables.
  2. **Bronze / silver / gold** : on garde le brut, on nettoie une fois, on sert des indicateurs. Sans silver, un `JOIN` fait disparaître des lignes **sans aucune erreur**.
  3. **On teste les données comme on teste du code** : `dbt build` refuse de servir la tasse si les grains sont mauvais. Avec Git et les PR, c'est le DataOps.

### ⚠️ À vérifier avant la séance

L'auteur de la version précédente n'a pas pu tout exécuter. Ces points sont à contrôler une fois, sur la version de dbt installée en salle, et à corriger dans le support si besoin :

| Point | Ce que dit le support | À vérifier | Plan B |
|---|---|---|---|
| `.gitignore` créé par `dbt init` | Contient `target/`, `dbt_packages/`, `logs/` | Ouvrir `datacafe_dbt/.gitignore` après `dbt init` | Le support dit déjà « s'il n'existe pas, créez-le avec ces trois lignes » |
| `SUBSTRING` à 2 arguments (`stg_ventes`) | `LOWER(SUBSTRING(TRIM(region), 2))` | Que DuckDB accepte la longueur facultative (`dbt run` passe et `paris` devient `Paris`) | Écrire `LOWER(SUBSTRING(TRIM(region), 2, LENGTH(TRIM(region))))`, valable partout |
| Avertissement `arguments:` (dbt 1.10+) | Encadré 🔬 : l'écriture sans `arguments:` marche, avec un simple avertissement jaune | Que `dbt test` passe sans `arguments:` et que l'avertissement n'est qu'un avertissement | Si la version de la salle le permet, prévenir les étudiants que le jaune n'est pas une erreur |
| `meta.external_location` (sources, encadré 🔬) | Un avertissement peut suggérer `config:` | Que la source fonctionne et ce que dit l'avertissement exact | Essayer `config:` → `meta:` → `external_location:` ; sinon garder l'avertissement |
| Sorties affichées (`dbt --version`, `dbt seed`, `dbt run`, `dbt test`) | Exemples de sortie | Ordre des lignes, temps, colonne `NO-OP`, numéros de version | Elles sont **approximatives** : dire aux étudiants de regarder `OK` / `PASS` / `ERROR` et les totaux, pas le texte exact |
| Version de Python | dbt peut ne pas encore supporter la toute dernière version de Python | `pip install dbt-core dbt-duckdb` dans un venv Python récent | Python 3.12 ou 3.13 |
| Nombre de tests | 9 tests (8 YAML + 1 singulier) | `dbt test` affiche `TOTAL=9` | Si `seeds.yml` (7.7 🟡) est déjà ajouté : 11 tests |

### Script de démonstration

**👀 Créer le projet (10 min).** Partir d'un dépôt `datacafe-streamlit` propre, `stenv` déjà activé, VS Code ouvert sur le dépôt, terminal intégré visible, police agrandie.

1. `git switch main`, `git pull`, `git switch -c pipeline-dbt`. Montrer la branche en bas à gauche de VS Code.
2. `dbt --version` : montrer `Core` et `Plugins: duckdb`.
3. `dbt init datacafe_dbt --skip-profile-setup`. Ouvrir l'arborescence dans VS Code, parcourir les dossiers (⭐ `models`, `seeds`, `tests`, `dbt_project.yml`). Ouvrir le `.gitignore` créé par dbt et **le montrer** (voir « À vérifier »).
4. `cd datacafe_dbt`, puis `pwd`. Supprimer `models/example`, créer `models/silver` et `models/gold`.
5. Remplacer `dbt_project.yml`. Montrer l'indentation avec la sélection (VS Code affiche les guides d'indentation). Lire `+materialized: view` / `table`.
6. Créer `profiles.yml`. Faire remarquer que `datacafe_dbt:` (ligne 1) = `profile:` de `dbt_project.yml`.
7. `dbt debug` → `All checks passed!`.
8. `git status` : montrer qu'on ne voit ni `target/`, ni `datacafe.duckdb` (la base n'existe pas encore d'ailleurs). `git add .`, `git commit -m "Création du projet dbt datacafe_dbt"`.

*Ce qui peut mal tourner :* `dbt debug` en erreur de profil parce qu'un `~/.dbt/profiles.yml` existe déjà sur la machine du professeur avec un autre nom ; c'est sans conséquence ici car dbt lit d'abord le dossier courant, mais vérifier la veille. Si le réseau est coupé, `dbt --version` met du temps à afficher « latest » : ignorer.

**👀 Premier modèle silver (10 min).** Avoir les seeds déjà chargés.

1. Créer `models/silver/stg_ventes.sql`, taper la requête bloc par bloc en commentant chaque ligne.
2. `dbt run` → `1 of 1 OK created sql view model main.stg_ventes`. Pointer « view ».
3. 🔬 Ouvrir `target/compiled/datacafe_dbt/models/silver/stg_ventes.sql` : montrer le `ref` remplacé. Puis `target/run/...` : le `create view ... as (...)`.
4. Bonus pédagogique (1 min) : ajouter un `;` à la fin, relancer `dbt run`, montrer l'erreur, enlever le `;`.

*Ce qui peut mal tourner :* *Could not set lock on file* si un terminal DuckDB est resté ouvert ; c'est la meilleure démonstration de l'avertissement `.quit`. Si `SUBSTRING` à 2 arguments est refusé, basculer sur la version avec `LENGTH` (voir « À vérifier »).

**👀 Couche gold et DAG (10 min).**

1. Créer `models/gold/ca_par_region.sql`, rappeler la jointure du chapitre 6.
2. `dbt run` → 2 modèles, `stg_ventes` d'abord. Demander : « Qui a dit à dbt de faire `stg_ventes` en premier ? »
3. `duckdb datacafe.duckdb`, `SELECT * FROM ca_par_region;`, `.quit`. Faire constater : Lyon et Paris ont atteint leur objectif, pas Marseille ni Lille.
4. Projeter le DAG mermaid. Puis `dbt run --select +ca_par_region` et `dbt run --select stg_ventes+` pour montrer la différence.

### Corrigés des exercices

**🛠️ 7.1 Bronze, silver ou gold ?**

1. 🥉 Bronze · 2. 🥇 Gold · 3. 🥈 Silver · 4. 🥇 Gold · 5. 🥉 Bronze · 6. 🥈 Silver

Le réflexe : **brut et intouché** → bronze ; **nettoyé, une ligne = un fait** → silver ; **agrégé pour une décision** → gold. Erreur fréquente : classer 6 en gold « parce que les montants sont en euros » ; ce n'est pas agrégé, donc silver.

**🛠️ 7.2 Le chantier est prêt.** Valider sur trois écrans : `dbt debug` → `All checks passed!` ; `git log --oneline` → le commit « Création du projet dbt » ; `git status` → propre, sans `target/`, `datacafe.duckdb` ni `stenv/`. Erreurs fréquentes : voir l'encadré 🆘 du support et le tableau « Pièges fréquents ». Si `stenv/` apparaît dans `git status`, le `.gitignore` du chapitre 5 manque : l'ajouter à la racine.

**🛠️ 7.3 Les graines de données.** Les 3 problèmes : une vente **en double** le 30 mars (Cappuccino, Marseille, 6), une ville écrite **`paris`** en minuscules le 31 mars, et une **quantité manquante** dans la dernière ligne (les deux virgules qui se suivent). `dbt seed` : `INSERT 4` (regions) et `INSERT 21` (ventes_brutes). Dans DuckDB, `.tables` liste `regions` et `ventes_brutes` ; la requête `WHERE date >= '2026-03-30'` renvoie 4 lignes (les deux doublons, `paris`, la ligne sans quantité).

**🛠️ 7.4 Le contrôle du torréfacteur.**

```sql
SELECT COUNT(*) FROM ventes_brutes;   -- 21
SELECT COUNT(*) FROM stg_ventes;      -- 19

SELECT COUNT(*) FROM stg_ventes    WHERE region = 'Paris';   -- 6
SELECT COUNT(*) FROM ventes_brutes WHERE region = 'Paris';   -- 5
```

1. **21 − 19 = 2 lignes** en moins : le doublon a été fusionné par `DISTINCT`, et la ligne sans quantité a été écartée par le `WHERE`.
2. **6 dans silver** contre **5 dans bronze** : la vente du 31 mars écrite `paris` est maintenant rattachée à `Paris`.

Erreurs fréquentes : oublier le `;` dans le terminal DuckDB (ici il est obligatoire, contrairement aux modèles dbt) ; oublier `.quit` puis lancer `dbt run` (erreur de verrou).

### Script de démonstration

**👀 Déclarer et lancer les tests (10 min).** Partir d'un projet où `dbt run` passe avec les 4 modèles.

1. Créer `models/silver/silver.yml` : taper la première colonne, copier-coller le reste, en lisant chaque test à voix haute.
2. Créer `models/gold/gold.yml`.
3. Créer `tests/assert_montant_positif.sql`. Lire le commentaire : « réussit si aucune ligne ».
4. `dbt test` → `PASS=9`. Compter avec la classe : 1 + 2 + 2 + 1 dans `silver.yml`, 2 dans `gold.yml`, 1 singulier = 9.
5. Si un avertissement jaune `arguments` apparaît : le montrer, ouvrir l'encadré 🔬, « jaune = avertissement, rouge = erreur ».

### Corrigés des exercices

**🛠️ 7.5 Votre propre carte des cafés.**

`models/gold/ca_par_produit.sql` :

```sql
-- Couche GOLD : ventes par café

SELECT
    produit,
    SUM(quantite) AS paquets_vendus,
    SUM(montant)  AS chiffre_affaires
FROM {{ ref('stg_ventes') }}
GROUP BY produit
```

`models/gold/ca_par_mois.sql` :

```sql
-- Couche GOLD : évolution mensuelle du chiffre d'affaires

SELECT
    strftime(date_vente, '%Y-%m') AS mois,
    COUNT(*)                      AS nb_ventes,
    SUM(montant)                  AS chiffre_affaires
FROM {{ ref('stg_ventes') }}
GROUP BY mois
```

Résultats :

- `ca_par_produit` : **Espresso 230 €** (23 paquets), Cappuccino 212,50 €, Moka 135 €, Latte 121 €.
- `ca_par_mois` : janvier 192 €, février 238 €, **mars 268,50 €** (total 698,50 €).

**Oui, le classement a changé.** Au chapitre 6, le Cappuccino menait en chiffre d'affaires (212,50 €) et l'Espresso en paquets (21). Grâce à la vente du 31 mars (2 Espresso à Paris, enfin rattachée), l'Espresso passe à 230 € et 23 paquets, devant le Cappuccino. Et le doublon n'a pas gonflé le Cappuccino. Sans couche silver, le directeur aurait reçu un classement faux.

Pas d'`ORDER BY` dans les modèles : c'est un choix courant, une table n'a pas d'ordre garanti, c'est l'outil d'affichage (Streamlit) qui trie.

Erreurs fréquentes : laisser `read_csv('ventes.csv')` au lieu de `ref('stg_ventes')` ; recalculer `quantite * prix_unitaire` au lieu d'utiliser `montant` (ça marche, mais c'est le signe que le rôle de silver n'est pas compris) ; écrire `strftime(date, ...)` alors que la colonne s'appelle `date_vente` ; laisser un `;`.

**🔴 Défi : le piège silencieux de la jointure.** Paris afficherait **202 €** au lieu de 222 € : la ligne `paris` ne trouve **aucune** correspondance dans `regions`, et le `JOIN` la fait **disparaître sans prévenir**. Marseille afficherait **236 €** au lieu de 161 € à cause du doublon (6 × 12,50 = 75 € comptés deux fois)... et Sofia aurait cru avoir atteint son objectif de 180 €. **Aucune erreur** ne s'afficherait. C'est pour cela qu'on nettoie en silver, et qu'on teste.

**🛠️ 7.6 Le saboteur.** Le test **`relationships`** sur la colonne `region` échoue :

```text
Failure in test relationships_stg_ventes_region__region__ref_regions_ (models/silver/silver.yml)
  Got 1 result, configured to fail if != 0
```

*« J'ai trouvé 1 ligne coupable »* : la ville `paris` n'existe pas dans `regions`. Les modèles **gold** qui dépendent de `stg_ventes` (`ca_par_region`, `ca_par_produit`, `ca_par_mois`) sont marqués **`SKIP`** (ainsi que les tests de `ca_par_region`) : dbt refuse de construire des indicateurs à partir de données silver qui n'ont pas passé le contrôle qualité. Le nom exact du test et la liste des `SKIP` peuvent varier légèrement selon la version.

🟡 La ligne coupable :

```sql
SELECT DISTINCT region FROM stg_ventes WHERE region NOT IN (SELECT region FROM regions);
-- paris
```

🔴 Second sabotage non détecté, exemples :

- **Supprimer le `DISTINCT`** : le doublon revient, aucun test ne le voit. Test qui l'attrape, `tests/assert_pas_de_doublon.sql` :

  ```sql
  SELECT date_vente, produit, region, quantite, prix_unitaire, COUNT(*) AS nb
  FROM {{ ref('stg_ventes') }}
  GROUP BY date_vente, produit, region, quantite, prix_unitaire
  HAVING COUNT(*) > 1
  ```

- **Changer le calcul du montant** (par exemple `quantite + prix_unitaire`) : tous les tests passent. Test : `SELECT * FROM {{ ref('stg_ventes') }} WHERE montant <> quantite * prix_unitaire`.
- À l'inverse, **supprimer le `WHERE quantite IS NOT NULL`** est bien détecté (le `not_null` sur `montant` échoue) : bon contre-exemple à faire découvrir.

Valider : l'étudiant sait expliquer le `SKIP` et `dbt build` est de nouveau vert, commit « Tests de qualité... » présent.

## Pièges fréquents et dépannage

| Symptôme | Cause | Solution |
|---|---|---|
| `dbt` : commande introuvable | `stenv` non activé, ou dbt non installé | Activer `stenv` (`(stenv)` doit apparaître) ; sinon `pip install -r requirements.txt` |
| Installation de dbt en erreur (rouge, Visual C++) | Python trop récent | Python 3.12 ou 3.13, recréer `stenv` |
| `No dbt_project.yml found` | Commande lancée hors de `datacafe_dbt` | `cd datacafe_dbt`, vérifier avec `pwd` |
| `Could not find profile named 'datacafe_dbt'` | Nom différent entre `profile:` et `profiles.yml`, ou `profiles.yml` mal placé | Aligner les noms ; `profiles.yml` à côté de `dbt_project.yml` |
| `mapping values are not allowed here` / `Runtime Error ... yaml` | Indentation YAML (tabulation, espace en trop) | Comparer espace par espace ; afficher les espaces dans VS Code |
| `[WARNING]` mentionnant `example` | Ancienne config `example` restée dans `dbt_project.yml` | Remplacer **tout** le contenu du fichier |
| `Could not set lock on file` | Terminal DuckDB ou Streamlit ouvert sur `datacafe.duckdb` | `.quit` dans DuckDB, fermer l'autre programme |
| Erreur de syntaxe près de `;` dans un modèle | Point-virgule à la fin du modèle | Le supprimer |
| `Compilation Error ... ref` / modèle introuvable | Faute de frappe dans `ref('...')` ou fichier mal nommé | Le nom dans `ref` = le nom du fichier sans `.sql` |
| `stg_ventes` toujours 21 lignes | Oubli du `DISTINCT` ou du `WHERE` | Comparer avec le support |
| `relationships` en échec sans sabotage | Correction de la ville incorrecte (ou `SUBSTRING` mal recopié) | Vérifier la ligne `UPPER(LEFT(...)) \|\| LOWER(SUBSTRING(...))` |
| Avertissement jaune `arguments` | dbt 1.10+ | Pas grave ; voir 🔬 du support |
| `Address already in use` (docs) | Port 8080 occupé | `dbt docs serve --port 8081` |
| Terminal « bloqué » après `dbt docs serve` | Le serveur tourne | `Ctrl + C`, ou ouvrir un second terminal |
| `Catalog Error: Table ... ca_par_region does not exist` | Base non construite, ou Streamlit lancé depuis le mauvais dossier | `cd datacafe_dbt && dbt build`, puis lancer Streamlit depuis `datacafe-streamlit` |
| `datacafe.duckdb` ou `target/` dans `git status` | `.gitignore` absent ou incomplet | `*.duckdb` à la racine, `target/`, `dbt_packages/`, `logs/` dans `datacafe_dbt/.gitignore` |
| CI GitHub rouge : profil introuvable | `profiles.yml` non versionné, ou workflow pas à la racine | Versionner `profiles.yml` ; `.github/workflows/` à la racine du dépôt |
