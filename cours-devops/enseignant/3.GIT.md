# Guide enseignant · Chapitre 3 · Introduction à Git
[← Support étudiant](../3.GIT.md)

## En bref

- **Durée** : 3h, en **2 séances de 1h30**.
  - Séance 1 · Mes premiers commits : vocabulaire, 3 zones, configuration, `git init`, premier commit, cycle quotidien.
  - Séance 2 · Voyager dans le temps : historique, HEAD et main, `git checkout`, tags, mission v4.0, défi enquêteur.
- **Matériel** : un ordinateur par étudiant avec VS Code (chapitre 2), Live Server et Git Graph installés ; vidéoprojecteur ; terminal du professeur en **police agrandie** (`Ctrl + +` dans VS Code) et thème clair si la salle est lumineuse.
- **À faire avant la séance 1** :
  - Envoyer aux étudiants, quelques jours avant, la consigne « installer Git » (section *Préparation* du support). Sur Mac, l'installation des *Command Line Tools* peut prendre 10 à 20 minutes : elle ne doit **pas** se faire en classe.
  - Préparer sur la machine du professeur un **dossier vide** pour la démo (supprimer l'ancien `~/cours-devops/site-datacafe` s'il existe, ou utiliser un autre compte), avec `hello.html` et `style.css` déjà téléchargés dans `~/Téléchargements` (secours si le Wi-Fi tombe). Les fichiers sont aussi dans `cours-devops-git/webapp/`.
  - Préparer pour l'animation physique : 3 feuilles A4 « 📂 COUR », « 📋 ESTRADE », « 🗄️ ALBUM » et 2 pancartes « hello.html » et « style.css » (voir Séance 1).
  - Prévoir une clé USB avec l'installateur Git for Windows pour les étudiants qui ne l'ont pas fait.
- **À faire avant la séance 2** : avoir sur la machine du professeur un dépôt avec les 3 commits de la séance 1 (celui de la démo, conservé).
- **Fil DataCafé** : les fichiers `accueil_final_VRAIMENT_final.html` ont fait perdre la version de la veille ; Léa demande de gérer la page de l'équipe avec Git pour pouvoir revenir à n'importe quelle version en une commande.
- **Les 3 messages clés** :
  1. Un **commit** est une photo de vos fichiers, avec un message : on ne perd plus jamais une version.
  2. Une modification passe par **3 zones** (travail → index → dépôt) ; `git add` choisit, `git commit` photographie.
  3. **On ne détruit rien en voyageant dans le temps** : `git checkout` déplace seulement HEAD, `git switch main` ramène au présent.
- **Continuité** : le dépôt `~/cours-devops/site-datacafe` (branche `main`, fichiers `hello.html` et `style.css`, tags `v1.0` à `v4.0`) est repris tel quel au chapitre 4 (`git remote add origin ...`, `git push --tags`). Insister pour que chacun le garde.

### Points d'animation

**💬 Tour de table.** Faire monter la tension : demander « qui a déjà perdu un travail parce qu'il avait écrasé le mauvais fichier ? ». Écrire au tableau 2 ou 3 noms de fichiers ridicules donnés par la classe : ils serviront de contre-exemple toute la séance (« avec Git, plus jamais de `_final_v3` »).

**🎤 Cours · Git, c'est quoi ?** Ne pas lire le tableau de vocabulaire en entier : ne commenter que les 5 premières lignes (repo, commit, index, log, tag). Dire explicitement que branch, merge, remote, clone, push/pull et fork seront vus au chapitre 4. L'anecdote de Linus (« sale gosse ») détend la salle : la garder.

**🎤 Cours · Les 3 zones : animation physique de la photo de classe (le moment clé de la séance).**

1. Poser au sol ou sur 3 tables les feuilles « 📂 COUR » (au fond ou sur le côté), « 📋 ESTRADE » (devant le tableau), « 🗄️ ALBUM » (le tableau lui-même).
2. Faire venir 2 volontaires avec les pancartes « hello.html » et « style.css », plus un 3e sans pancarte « brouillon.txt ». Ils se placent dans la COUR. Le professeur joue le **photographe**.
3. Demander à la classe : « `git status` ? » La classe répond : « 3 élèves dans la cour, personne sur l'estrade » (*untracked*).
4. Dire « `git add hello.html` » : l'élève monte sur l'ESTRADE. « `git add style.css` » : idem. brouillon.txt reste dans la cour.
5. Dire « `git commit -m "Première photo"` » : prendre réellement une photo avec le téléphone (ou dessiner les 2 élèves au tableau dans un cadre « Photo 1 : Première photo »). Les élèves restent dans la classe : la photo est dans l'ALBUM, les fichiers ne disparaissent pas.
6. Rebondir : hello.html met une casquette (= il est **modifié**) mais reste dans la cour. « Est-il sur la photo 1 avec sa casquette ? » Non. « Que faut-il faire pour une photo avec casquette ? » `git add` puis `git commit`.
7. Bonus `git restore --staged` : hello.html monte sur l'estrade puis on le fait redescendre sans lui retirer sa casquette (la modification n'est pas perdue).

Ensuite seulement, projeter le mermaid et `images/git9.png` : les étudiants doivent reconnaître ce qu'ils viennent de voir. Garder la photo prise : elle peut servir en séance 2 (« on peut toujours ressortir la photo 1 de l'album » = `git checkout`).

**Démos et exercices : la règle d'or.** Pendant chaque 👀, demander **écrans baissés ou mains loin du clavier**. Les débutants qui tapent en même temps que le professeur prennent du retard et ratent l'explication. Ensuite, les étudiants refont tout dans le 🛠️ en s'appuyant sur le support.

**Gestion des niveaux.**
- Former des **binômes mixtes** (un étudiant à l'aise + un débutant) avant l'exercice 3.1 : le plus rapide aide sans toucher au clavier de l'autre.
- Les rapides : 🟡 de chaque exercice, puis « aider un voisin » (ils deviennent assistants).
- Les débutants : leur faire lire à voix haute le message de `git status` ; Git dit souvent quoi faire (`use "git add" to track`).
- Un étudiant sans Git installé : le mettre en binôme sur l'écran du voisin pour les exercices 3.1 et 3.2 pendant que l'installation tourne, puis il rattrape.

**Si l'on est en retard.** Couper dans cet ordre : l'encadré « pour les curieux » (centralisé/distribué), le 🟡 de l'exercice 3.3, le quiz « Le premier commit » (le faire en ouverture de la séance 2). Ne **jamais** couper l'animation des 3 zones ni l'exercice 3.2.

### Script de démonstration

> Les sorties ci-dessous ont été obtenues avec Git 2.43 en anglais. Les identifiants (SHA) seront différents. Sur un Mac ou un Linux réglé en français, Git peut répondre en français : `Sur la branche main`, `Aucun commit`, `Fichiers non suivis`, `rien à valider, la copie de travail est propre`. Prévenir la classe que les deux versions existent.

#### 👀 Démo 1 · Configurer Git et créer le dépôt (5 min)

1. Ouvrir VS Code, terminal **Git Bash** (Windows) ou Terminal (Mac). Taper :

   ```bash
   git --version
   ```

   Sortie attendue : `git version 2.4x.x`.

2. Configuration (utiliser son vrai nom, et dire à voix haute : « même e-mail que votre futur compte GitHub ») :

   ```bash
   git config --global user.name "Prénom Nom"
   git config --global user.email "prenom.nom@example.com"
   git config --global init.defaultBranch main
   git config --global core.editor "code --wait"
   git config --global color.ui auto
   git config --list --global
   ```

   Faire remarquer : ces commandes **ne répondent rien** quand tout va bien (« pas de nouvelles, bonnes nouvelles »). Seul `--list` affiche :

   ```text
   user.name=Prénom Nom
   user.email=prenom.nom@example.com
   init.defaultbranch=main
   core.editor=code --wait
   color.ui=auto
   ```

3. Création du dépôt :

   ```bash
   cd ~/cours-devops
   mkdir site-datacafe
   cd site-datacafe
   git init
   ```

   Sortie : `Initialized empty Git repository in /home/.../cours-devops/site-datacafe/.git/`

   ```bash
   ls -a
   ```

   Sortie : `.  ..  .git`. Faire remarquer : « Le dossier semble vide avec `ls`, mais `.git` est là : c'est l'album photo. Si on le supprime, on perd tout l'album. »

4. `code .` : VS Code s'ouvre sur le dossier vide.

**Ce qui peut mal tourner en direct** : `ls -a` refusé dans PowerShell (passer en Git Bash, c'est l'occasion de montrer comment changer de terminal) ; `mkdir: cannot create directory: File exists` si le dossier existe déjà (c'est sans gravité : `cd site-datacafe`).

#### 👀 Démo 2 · Mon premier commit (8 min)

1. ```bash
   git status
   ```

   ```text
   On branch main

   No commits yet

   nothing to commit (create/copy files and use "git add" to track)
   ```

   Dire : « Git est poli, il nous dit même quoi faire : copier des fichiers et utiliser `git add`. »

2. Télécharger `hello.html` et `style.css` depuis GitHub (bouton **Download raw file**), les déplacer dans `site-datacafe` (montrer où ils atterrissent : `Téléchargements`). Clic droit sur `hello.html` → **Open with Live Server** : la page « Bienvenue dans cette formation GIT ! » s'affiche.

3. ```bash
   git status
   ```

   ```text
   On branch main

   No commits yet

   Untracked files:
     (use "git add <file>..." to include in what will be committed)
   	hello.html
   	style.css

   nothing added to commit but untracked files present (use "git add" to track)
   ```

   Demander : « Dans quelle zone sont-ils ? » (la cour).

4. ```bash
   git add hello.html
   git add style.css
   git status
   ```

   ```text
   On branch main

   No commits yet

   Changes to be committed:
     (use "git rm --cached <file>..." to unstage)
   	new file:   hello.html
   	new file:   style.css
   ```

   Faire remarquer le **passage du rouge au vert** (sur l'estrade).

5. ```bash
   git commit -m "Ajout de la page d'accueil et de sa feuille de style"
   ```

   ```text
   [main (root-commit) fb79137] Ajout de la page d'accueil et de sa feuille de style
    2 files changed, 101 insertions(+)
    create mode 100644 hello.html
    create mode 100644 style.css
   ```

   Commenter : `main` = la branche, `root-commit` = le tout premier, `fb79137` = l'identifiant (sa plaque d'immatriculation).

6. ```bash
   git status
   ```

   ```text
   On branch main
   nothing to commit, working tree clean
   ```

   Dire : « *working tree clean* : tout est dans l'album. C'est l'état à viser à la fin de chaque exercice. »

**Ce qui peut mal tourner** : le navigateur enregistre `hello.html.txt` ou la page GitHub entière au lieu du fichier brut (bien cliquer sur **Download raw file**) ; oubli de `-m` : Git ouvre un éditeur (VS Code si `core.editor` est réglé : écrire le message, **enregistrer et fermer l'onglet** ; sinon Vim : `Échap`, `:q!`, Entrée). Profiter de l'incident pour montrer la solution à la classe.

#### 👀 Démo 3 · Le cycle quotidien (8 min)

1. Dans `hello.html`, ligne 15, remplacer `<div>` par `<div id="top-banner">`, enregistrer (`Ctrl + S`). Live Server recharge : bannière sombre.
2. ```bash
   git diff hello.html
   ```

   ```text
   diff --git a/hello.html b/hello.html
   index 1997910..4434ad2 100644
   --- a/hello.html
   +++ b/hello.html
   @@ -12,7 +12,7 @@
    	<body>
    
    		<!-- TITRE -->
   -		<div>
   +		<div id="top-banner">
    			Bienvenue dans cette formation GIT !
    		</div>
   ```

   Faire lire la ligne `-` et la ligne `+`. Dire : « Une ligne modifiée = une ligne supprimée + une ligne ajoutée. »

3. ```bash
   git add hello.html
   git status
   ```

   ```text
   On branch main
   Changes to be committed:
     (use "git restore --staged <file>..." to unstage)
   	modified:   hello.html
   ```

   Faire remarquer que Git **suggère lui-même** la commande pour annuler.

4. ```bash
   git restore --staged hello.html
   git status
   ```

   ```text
   On branch main
   Changes not staged for commit:
     (use "git add <file>..." to update what will be committed)
     (use "git restore <file>..." to discard changes in working directory)
   	modified:   hello.html

   no changes added to commit (use "git add" and/or "git commit -a")
   ```

   Rappeler la casquette : redescendu de l'estrade, mais toujours modifié.

5. ```bash
   git add hello.html
   git commit -m "Ajout de la bannière en haut de la page"
   git status
   ```

   Sortie : `[main c5c7496] Ajout de la bannière en haut de la page`, `1 file changed, 1 insertion(+), 1 deletion(-)`, puis `working tree clean`.

6. Projeter le tableau **bouton panique** et insister sur l'avertissement de `git restore hello.html` (modification perdue définitivement, aucune corbeille). Ne pas démontrer `--amend` si l'on manque de temps.

7. **Faire aussi le commit « Ajout d'une description »** sur la machine du professeur (pendant l'exercice 3.3 ou juste après) : il faut 3 commits pour la séance 2.

### Corrigés des exercices

**Exercice 3.1 · Préparer votre dépôt**

```bash
git --version
git config --global user.name "Prénom Nom"
git config --global user.email "prenom.nom@example.com"
git config --global init.defaultBranch main
git config --global core.editor "code --wait"
git config --global color.ui auto
git config --list --global
cd ~/cours-devops
mkdir site-datacafe
cd site-datacafe
git init
code .
```

- Valider : `git config --list --global` montre `user.name`, `user.email`, `init.defaultbranch=main` ; `ls -a` montre `.git`.
- 🟡 Si on supprime `.git` : le dossier redevient un dossier ordinaire, **tout l'historique est perdu** (les fichiers actuels restent).
- Erreurs fréquentes : guillemets oubliés autour du nom (`git config --global user.name Prénom Nom` n'enregistre que « Prénom ») ; faute dans l'e-mail ; `git init` lancé dans `~` ou dans `cours-devops` au lieu de `site-datacafe` (voir dépannage) ; `~/cours-devops` absent (étudiant absent au chapitre 2 : `mkdir -p ~/cours-devops`).

**Exercice 3.2 · Votre premier commit**

```bash
git status
# (téléchargement de hello.html et style.css dans site-datacafe)
git status
git add hello.html
git add style.css
git status
git commit -m "Ajout de la page d'accueil et de sa feuille de style"
git status
```

- Valider : `nothing to commit, working tree clean` et `git log --oneline` montre 1 commit.
- 🟡 Zones : `git status` = on regarde ; `git add` = cour → estrade ; `git commit` = estrade → album.
- Erreurs fréquentes : fichiers restés dans `Téléchargements` (`git status` ne voit rien) ; `Author identity unknown *** Please tell me who you are` si l'exercice 3.1 n'est pas fini (refaire les deux `git config`) ; `git add .` exécuté dans le mauvais dossier.

**Exercice 3.3 · La bannière et votre présentation**

```bash
# 1. Bannière : <div> remplacé par <div id="top-banner"> dans hello.html
git diff hello.html
git add hello.html
git restore --staged hello.html
git add hello.html
git commit -m "Ajout de la bannière en haut de la page"

# 2-3. Présentation ajoutée sous la bannière
git status
git add hello.html
git commit -m "Ajout d'une description"
git status
```

Le bloc ajouté dans `hello.html`, juste après le `</div>` de la bannière :

```html
<!-- description -->
<div>
    <p>Bonjour, je m'appelle ... et je viens de rejoindre DataCafé !</p>
</div>
```

- Valider : bannière + phrase visibles dans le navigateur, `git log --oneline` montre 3 commits, `working tree clean`.
- 🟡 Modification ratée non indexée → `git restore hello.html` (et constater qu'elle a disparu).
- Erreurs fréquentes : fichier non enregistré dans VS Code (point blanc sur l'onglet) donc `git status` ne voit rien ; bloc collé **à l'intérieur** de la bannière ; message `modif` (le faire corriger avec `git commit --amend -m "..."`, c'est l'occasion de pratiquer).

### Points d'animation

**💬 Tour de table.** Profiter de la 3e question pour que chacun se place dans son dépôt (`cd ~/cours-devops/site-datacafe`) **avant** la suite. Puis l'analogie du livre : un étudiant tient un livre ouvert à la dernière page (main), un marque-page (HEAD). On déplace le marque-page en arrière : la dernière page n'est pas arrachée. Poser la question « si je relis la page 1, les pages 2 et 3 sont-elles effacées ? » (préparation de la Q5 du quiz).

**🛠️ Mission finale.** Lancer les trois niveaux en même temps : chacun avance à son rythme. Valider individuellement la v4.0 (le professeur passe et regarde `git log --oneline`). ### Script de démonstration

#### 👀 Démo 4 · Explorer l'historique (8 min)

1. ```bash
   cd ~/cours-devops/site-datacafe
   git log
   ```

   ```text
   commit 89089f25efb8d0147267164a5b94fdb1669f99ee (HEAD -> main)
   Author: Prénom Nom <prenom.nom@example.com>
   Date:   Mon Oct 5 09:42:06 2026 +0200

       Ajout d'une description

   commit c5c74963...
   ...
   ```

   Faire remarquer : l'identifiant de 40 caractères, l'auteur (c'est la config de la séance 1 !), la date, l'ordre **du plus récent au plus ancien**. Si la liste remplit l'écran : `q`.

2. ```bash
   git log -n 1
   git log --oneline
   ```

   ```text
   89089f2 (HEAD -> main) Ajout d'une description
   c5c7496 Ajout de la bannière en haut de la page
   fb79137 Ajout de la page d'accueil et de sa feuille de style
   ```

   Dire : « Les 7 premiers caractères suffisent. Vos identifiants sont différents des miens : ne recopiez jamais ceux du projecteur ni ceux du support. »

3. ```bash
   git log --oneline --graph --all
   ```

   Puis `Ctrl + Maj + P` → **Git Graph: View Git Graph** pour la version visuelle.

4. ```bash
   git show c5c7496
   ```

   Montrer en bas le diff `-<div>` / `+<div id="top-banner">`.

#### 👀 Démo 5 · Voyager dans le temps (7 min)

1. ```bash
   git checkout fb79137    # identifiant du premier commit de la machine du professeur
   ```

   ```text
   Note: switching to 'fb79137'.

   You are in 'detached HEAD' state. You can look around, make experimental
   changes and commit them, and you can discard any commits you make in this
   state without impacting any branches by switching back to a branch.
   ...
   HEAD is now at fb79137 Ajout de la page d'accueil et de sa feuille de style
   ```

2. Basculer sur le navigateur : bannière et description ont disparu. Montrer aussi `hello.html` dans VS Code.
3. ```bash
   git status
   ```

   ```text
   HEAD detached at fb79137
   nothing to commit, working tree clean
   ```

   Faire remarquer que `On branch main` a été remplacé par `HEAD detached at` : c'est **le** signe qu'on visite le passé.

4. ```bash
   git switch main
   ```

   ```text
   Previous HEAD position was fb79137 Ajout de la page d'accueil et de sa feuille de style
   Switched to branch 'main'
   ```

   Retour au navigateur : tout est revenu.

**Ce qui peut mal tourner** : `error: pathspec '1a4e6f2' did not match any file(s) known to git` = identifiant recopié du support au lieu du sien (en faire un exemple pour la classe). Live Server ne recharge pas : `F5` dans le navigateur.

#### 👀 Démo 6 · Les tags (5 min)

```bash
git tag -a v1.0 fb79137 -m "Version 1 : page d'accueil"
git tag -a v2.0 c5c7496 -m "Version 2 : ajout de la bannière"
git tag -a v3.0 -m "Version 3 : ajout de la description"
git tag
git log --oneline
```

```text
v1.0
v2.0
v3.0
89089f2 (HEAD -> main, tag: v3.0) Ajout d'une description
c5c7496 (tag: v2.0) Ajout de la bannière en haut de la page
fb79137 (tag: v1.0) Ajout de la page d'accueil et de sa feuille de style
```

Puis :

```bash
git checkout v1.0
git checkout v2.0
git switch main
```

Faire remarquer que le message *detached HEAD* réapparaît : c'est normal, un tag est aussi un point du passé. Faire le lien avec l'étape **📦 Release** de la boucle DevOps et annoncer que ces tags apparaîtront sur GitHub au chapitre 4.

**Ce qui peut mal tourner** : `fatal: Failed to resolve '1a4e6f2' as a valid ref.` (identifiant du support recopié) ; `fatal: tag 'v2.0' already exists` (tag déjà posé, éventuellement sur le mauvais commit : `git tag -d v2.0` puis le recréer).

### Réponses du quiz

**Quiz · L'historique**

| Q | Réponse | Explication | Piège typique |
|---|---|---|---|
| Q1 | **B.** `git log --oneline` | Une ligne par commit : identifiant court + message. | A existe mais montre l'état des fichiers ; C n'existe pas. |
| Q2 | **B.** C'est le marque-page. | HEAD = là où l'on se trouve maintenant. | A (le premier commit) ; ne pas confondre avec main. |
| Q3 | `git switch main` (ou `git checkout main`). | Ramène HEAD sur le dernier commit de main. | Refaire `git checkout` avec l'identifiant du dernier commit : on reste en *detached HEAD*. |
| Q4 | **B.** | Un nom lisible pour une version publiée. | D (envoyer sur Internet), c'est `git push` (chapitre 4). |
| Q5 | **Faux !** | Les commits récents sont toujours là, et `main` pointe toujours dessus. On ne fait que « relire une ancienne page ». | La peur de tout perdre : c'est justement le message à faire passer. |

### Corrigés des exercices

**Exercice 3.4 · Explorer et voyager**

```bash
cd ~/cours-devops/site-datacafe
git status
git log
git log --oneline
git show <identifiant-du-commit-bannière>
git checkout <identifiant-du-premier-commit>
git switch main
```

- Valider : l'étudiant a vu la page sans bannière, puis `git status` affiche `On branch main`.
- 🟡 `git log --oneline --graph --all` : une ligne droite de 3 commits, HEAD et main sur le plus récent ; pendant le voyage, HEAD est sur le premier commit et main reste en haut (même chose dans Git Graph).
- Erreurs fréquentes : identifiant recopié du support ; `q` oublié dans `git log` ; modification faite pendant le voyage (voir dépannage).

**Exercice 3.5 · Étiqueter vos versions**

```bash
git tag -a v1.0 <id-commit-1> -m "Version 1 : page d'accueil"
git tag -a v2.0 <id-commit-2> -m "Version 2 : ajout de la bannière"
git tag -a v3.0 -m "Version 3 : ajout de la description"
git tag
git log --oneline
git checkout v1.0
git checkout v2.0
git switch main
```

- Valider : `tag: v1.0` sur le commit « page d'accueil », `tag: v2.0` sur « bannière », `tag: v3.0` sur « description ».
- 🟡 `git show v2.0` affiche d'abord le tag lui-même (`tag v2.0`, `Tagger`, date, message) puis le commit. Une étiquette annotée garde **qui** a publié la version, **quand** et **pourquoi**, avec un nom lisible.
- Erreurs fréquentes : `v3.0` posé alors que l'étudiant est encore en *detached HEAD* sur un vieux commit (le tag tombe sur le mauvais commit : `git switch main`, `git tag -d v3.0`, recréer) ; tags posés dans le désordre.

**Mission finale · 🟢 Vos passions (v4.0)**

```bash
git status
git add hello.html
git commit -m "Ajout de mes passions"
git tag -a v4.0 -m "Version 4 : ajout des passions"
git log --oneline
```

Résultat attendu :

```text
f81c2d9 (HEAD -> main, tag: v4.0) Ajout de mes passions
c3f9a1e (tag: v3.0) Ajout d'une description
8b27d40 (tag: v2.0) Ajout de la bannière en haut de la page
1a4e6f2 (tag: v1.0) Ajout de la page d'accueil et de sa feuille de style
```

Exemple de passions ajoutées dans la section description (le contenu exact est libre, voir `images/git18.png`) :

```html
<p>Mes passions : le café, la data et le football.</p>
```

- Valider : 4 commits, 4 tags, `(HEAD -> main, tag: v4.0)` en haut. **Indispensable pour le chapitre 4.**
- Erreurs fréquentes : mission faite en *detached HEAD* (oubli de l'étape 1) : voir « panique detached HEAD » dans le dépannage ; `git tag -a v4.0` posé **avant** le commit (le tag tombe sur v3.0 : `git tag -d v4.0`, commiter, reposer le tag).

**Mission finale · 🟡 Le voyage dans le temps**

```bash
git checkout v2.0       # la page n'a que la bannière, sans description ni passions
git switch main         # retour au présent
git diff v1.0 v4.0      # toutes les lignes ajoutées depuis la v1 (q pour quitter)
```

`git diff v1.0 v4.0` montre la ligne `-<div>` / `+<div id="top-banner">` et les lignes `+` de la description et des passions (environ `6 insertions(+), 1 deletion(-)` avec `git diff --stat v1.0 v4.0`).

**Mission finale · 🔴 Défi : l'enquêteur**

1. **4 commits** : `git log --oneline` (4 lignes) ou `git rev-list --count main` qui affiche `4`.
2. Date du commit bannière : `git log` (ligne `Date:` du commit « Ajout de la bannière »), ou plus directement `git show v2.0` ou `git log -n 1 v2.0`.
3. Ligne ajoutée dans `v3.0` : `git show v3.0` ; les lignes `+` sont le bloc description, en particulier `<p>Bonjour, je m'appelle ... et je viens de rejoindre DataCafé !</p>`.
4. `git blame hello.html` affiche, **pour chaque ligne** du fichier, le commit, l'auteur et la date de sa dernière modification. Exemple :

   ```text
   ^fb79137 (Prénom Nom 2026-10-05 09:41:57 +0200 14) 		<!-- TITRE -->
   c5c74963 (Prénom Nom 2026-10-05 09:42:06 +0200 15) 		<div id="top-banner">
   89089f25 (Prénom Nom 2026-10-05 09:42:06 +0200 18) 		<!-- description -->
   ```

   Le `^` indique une ligne qui vient du tout premier commit. Utilité en équipe : savoir qui a écrit une ligne et pourquoi (en lisant le message du commit), pas « blâmer » quelqu'un.

## Pièges fréquents et dépannage

| Symptôme | Cause | Solution |
|---|---|---|
| `git: command not found` / `'git' n'est pas reconnu...` | Git non installé, ou VS Code ouvert avant l'installation. | Fermer et rouvrir VS Code. Sinon installer (clé USB pour Windows) et faire travailler l'étudiant en binôme pendant l'installation. Sur Mac, lancer `git --version` pour déclencher les *Command Line Tools* (10 à 20 min). |
| Écran bizarre avec des `~` à gauche, impossible de taper du texte normal (**piège de Vim**) | `git commit` sans `-m` et `core.editor` non réglé. | `Échap`, `:q!`, Entrée. Puis relancer avec `-m "message"`. Pour éviter la récidive : `git config --global core.editor "code --wait"` si `code` marche. |
| Un onglet `COMMIT_EDITMSG` s'ouvre dans VS Code et le terminal attend | `git commit` sans `-m` avec `core.editor "code --wait"`. | Écrire le message sur la première ligne, enregistrer, **fermer l'onglet** : le commit se termine. |
| `code: command not found` | Commande `code` absente du PATH (chapitre 2). | Windows : fermer et rouvrir VS Code. Mac : palette `Cmd + Maj + P` → **Shell Command: Install 'code' command in PATH**. En attendant : **Fichier > Ouvrir le dossier**, et ne pas régler `core.editor` (non bloquant). |
| `git log` ou `git diff` ne rend pas la main, `(END)` ou `:` en bas | Affichage page par page (*pager*). | Appuyer sur **q**. |
| `fatal: not a git repository (or any of the parent directories): .git` | Terminal dans le mauvais dossier. | `pwd`, puis `cd ~/cours-devops/site-datacafe`. |
| `git status` liste des dizaines de fichiers inconnus (Documents, Bureau...) | `git init` lancé dans le dossier personnel `~` (ou dans `cours-devops`). | **Avec le professeur** : aller dans le bon dossier où le `.git` a été créé par erreur (`cd ~` ou `cd ~/cours-devops`), vérifier avec `ls -a`, puis `rm -rf .git` **uniquement à cet endroit**. Refaire `git init` dans `site-datacafe`. |
| `git status` ne voit pas `hello.html` | Fichier resté dans Téléchargements, enregistré sous `hello.html.txt`, ou modification non enregistrée dans VS Code. | `ls` pour vérifier, déplacer le fichier, renommer, `Ctrl + S`. |
| La page dans le navigateur est la page GitHub entière | Clic droit « Enregistrer sous » sur la page GitHub au lieu de **Download raw file**. | Retélécharger avec le bon bouton, ou copier `cours-devops-git/webapp/` fourni par le professeur. |
| `Author identity unknown *** Please tell me who you are.` | `user.name` / `user.email` non configurés. | Refaire les deux `git config --global` de l'exercice 3.1, puis relancer le commit. |
| `ls: unknown option -a` ou erreur de paramètre ambigu | Terminal PowerShell sur Windows. | Passer en **Git Bash** (flèche ˅ à côté du **+**). Toujours recommander Git Bash pour ce cours. |
| `warning: LF will be replaced by CRLF` | Fins de ligne Windows. | Sans gravité, ignorer. |
| **Panique *detached HEAD*** : « j'ai tout perdu, ma bannière a disparu ! » | L'étudiant est resté sur un ancien commit après `git checkout`. | `git status` affiche `HEAD detached at ...` → `git switch main`. Rassurer : rien n'est effacé. |
| `error: Your local changes to the following files would be overwritten by checkout` en faisant `git switch main` | Fichier modifié pendant la visite du passé. | Si la modification est sans valeur : `git restore hello.html` puis `git switch main`. Sinon, copier le texte ailleurs, restaurer, revenir sur main et refaire la modification. |
| `Warning: you are leaving 1 commit behind` après `git switch main` | Commit fait en *detached HEAD* (souvent la mission v4.0). | Git affiche l'identifiant du commit « abandonné » : rien n'est perdu. Sur main, afficher ce qu'il contenait avec `git show <identifiant>`, refaire la même modification dans `hello.html`, commiter, puis poser (ou reposer avec `git tag -d v4.0`) le tag `v4.0`. Ne pas utiliser `git merge` ici : le commit part d'une ancienne version et provoquerait un conflit. |
| `error: pathspec '1a4e6f2' did not match...` / `fatal: Failed to resolve '1a4e6f2' as a valid ref.` | Identifiant recopié du support ou du projecteur. | Utiliser les identifiants de **son** `git log --oneline`. |
| `fatal: tag 'v4.0' already exists` ou tag sur le mauvais commit | Tag posé deux fois ou au mauvais moment. | `git tag -d v4.0` puis le recréer au bon endroit. |
| Live Server n'affiche pas les changements | Fichier non enregistré, ou onglet ouvert sur un autre dossier. | `Ctrl + S`, `F5` ; relancer **Open with Live Server** depuis `site-datacafe`. |

  - Créer un fichier `.gitignore` contenant `*.log`, créer `test.log` et observer `git status`. À quoi cela sert-il dans un projet data (fichiers de données, mots de passe) ?
