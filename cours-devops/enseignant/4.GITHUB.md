# Guide enseignant · Chapitre 4 · Introduction à GitHub
[← Support étudiant](../4.GITHUB.md)

## En bref

- **Durée :** 3h30, en **2 séances de 1h45**.
  - Séance 1 : Git ou GitHub, mise en ligne de `site-datacafe` (push, tags, README), profil GitHub, puis dépôt d'équipe `equipe-datacafe` (clone, cartes de membres, pull) et **conflit volontaire** au signal.
  - Séance 2 : branches (solo), Pull Requests (recettes), issues et Kanban (mini-sprint), interfaces graphiques, release `v1.0` de l'équipe.
- **Matériel :** un ordinateur par étudiant avec Git configuré (`user.name`, `user.email`, `init.defaultBranch main`, `core.editor "code --wait"`) et le dépôt `site-datacafe` du chapitre 3 avec les tags `v1.0` à `v4.0`. Vidéoprojecteur, accès Internet vers `github.com` (HTTPS, port 443). Un minuteur projeté pour les phases d'équipe.
- **Ce qui doit être prêt avant la séance 1 :**
  - Comptes GitHub **créés et e-mail validé** par tous les étudiants (message à envoyer une semaine avant : voir « Préparation » ci-dessous).
  - Un tableau (feuille partagée ou au tableau blanc) : équipe, prénom, pseudo GitHub, chef d'équipe.
  - Le dépôt de démonstration du professeur (voir « Préparation »).
  - Les équipes de 4 constituées (les mêmes que pour le projet d'évaluation).
- **Fil DataCafé :** Léa fait passer l'équipe sur GitHub : chacun sur sa branche, relecture obligatoire, rien en production sans vérification.
- **Les 3 messages clés :**
  1. Git est le logiciel (local), GitHub est le service en ligne (partage, sauvegarde, collaboration).
  2. **La règle d'or :** toujours `git pull` avant de travailler et avant de `git push`. Un conflit n'est pas une erreur, c'est une question posée à l'équipe.
  3. En équipe, on ne touche pas `main` directement : **branche → Pull Request → relecture → fusion** (le GitHub Flow, qui sera utilisé dans tout le projet).

## Préparation (J-7 et jour J)

### Message aux étudiants, une semaine avant

> Pour la prochaine séance, créez votre compte sur github.com avec **la même adresse e-mail que celle configurée dans Git** (`git config --global user.email`), choisissez un pseudo professionnel, **validez votre e-mail** et notez votre pseudo dans le tableau partagé. Si GitHub vous demande d'activer la double authentification, ayez votre téléphone avec une application d'authentification. Apportez votre ordinateur avec votre dépôt `site-datacafe`.

Pourquoi avant ? Une trentaine d'inscriptions depuis la même adresse IP de l'école peut déclencher des captchas à répétition, des e-mails de validation qui tardent, voire un blocage temporaire. On perd facilement 20 minutes en classe.

### Constituer les équipes de 4

- Reprendre les équipes du projet d'évaluation. Si elles n'existent pas encore, les former **avant** la séance 1 : mélanger les niveaux, avec au moins **un étudiant à l'aise** (« référent Git ») par équipe.
- **Chef d'équipe 👑 :** un étudiant dont le `git push` a fonctionné pendant la première partie de la séance 1 (c'est lui qui crée le dépôt et invite les autres). Éviter de nommer chef celui qui a encore un problème d'authentification.
- Effectif non divisible par 4 : faire des équipes de 3 (le chef prend 2 issues au sprint) ou de 5 (le cinquième crée une issue supplémentaire « Ajouter une page `equipe.md` »). Éviter les équipes de 2 : le conflit et la relecture perdent leur intérêt.
- Les membres d'une même équipe s'assoient **côte à côte** dès le début de la partie 4.2.

### Le dépôt de démonstration du professeur

Prévoir, sur le compte GitHub du professeur :

1. **Un dépôt local `site-datacafe` prêt à pousser**, avec 4 commits et les tags `v1.0` à `v4.0`, mais **sans dépôt GitHub correspondant** (on le crée en direct). Réutiliser celui de la démonstration du chapitre 3, ou le reconstruire avec ce script (testé) :

   ```bash
   mkdir -p ~/demo/site-datacafe && cd ~/demo/site-datacafe
   git init
   # copier hello.html et style.css depuis le dossier webapp/ du cours
   git add . && git commit -m "Page d'accueil" && git tag -a v1.0 -m "Version 1 : page d'accueil"
   echo '<!-- bannière -->' >> hello.html
   git commit -am "Ajout de la bannière en haut de la page" && git tag -a v2.0 -m "Version 2 : ajout de la bannière"
   echo '<p>Bonjour, je suis le professeur.</p>' >> hello.html
   git commit -am "Ajout de la description" && git tag -a v3.0 -m "Version 3 : ajout de la description"
   echo '<p>Passions : ...</p>' >> hello.html
   git commit -am "Ajout des passions" && git tag -a v4.0 -m "Version 4 : ajout des passions"
   git log --oneline --decorate
   ```

   Si un dépôt `site-datacafe` existe déjà sur le compte (année précédente), le supprimer ou le renommer avant la séance.

2. **Un dépôt d'équipe de démonstration `equipe-prof`** (public, avec README), déjà cloné **deux fois** dans deux dossiers (`~/demo/equipe-prof` et `~/demo/equipe-prof-bis`) pour simuler deux coéquipiers sur le même écran (rejet de push, conflit). Préparer aussi une branche `ajout-recette-prof` déjà poussée, pour montrer en 2 minutes l'ouverture d'une PR en séance 2.
3. **Un deuxième compte GitHub** (compte de test du professeur ou collègue) invité comme collaborateur de `equipe-prof`, pour montrer une relecture **Approve** (on ne peut pas approuver sa propre PR). À défaut, demander à un étudiant volontaire de relire la PR en direct : c'est même plus vivant.
4. Navigateur **déjà connecté** à GitHub, VS Code avec l'extension **Git Graph**, police du terminal agrandie, et l'identification Git déjà testée la veille (un `git push` sur `equipe-prof`).
5. Vérifier la veille, depuis le réseau de la salle, que `git clone https://github.com/...` fonctionne (certains réseaux d'école filtrent). Prévoir un partage de connexion téléphone en secours.

### Points d'animation

**💬 Tour de table.** Faire émerger les mauvaises pratiques (« mémoire_v3_final_VRAIMENT_final.docx », fichiers envoyés par mail, Google Docs où tout le monde écrit en même temps). Question 3 : « Votre ordinateur tombe en panne : il vous reste quoi ? » La réponse (« rien ») justifie le dépôt distant. Compter les comptes GitHub manquants et lancer leur création immédiatement, sur téléphone si besoin.

**🎤 Git ou GitHub.** Insister sur le fait que Git fonctionne sans Internet : on a tout fait au chapitre 3 sans GitHub. Citer GitLab et Bitbucket pour montrer que la compétence est transférable. Faire noter le vocabulaire : *remote*, `origin`, `push`, `pull`, `clone`.

**🛠️ Mettre votre site en ligne.** C'est la phase la plus risquée de la séance (authentification).
- Débutants : les faire travailler en **binôme**, l'un tape, l'autre lit les consignes, puis on échange.
- Rapides (🟡) : les nommer « assistants » et leur demander d'aider un voisin bloqué, puis passer au profil.
- Si au bout de 15 minutes plus d'un quart de la classe est bloqué sur l'authentification, faire une **mini-démo collective du jeton** (PAT) au vidéoprojecteur plutôt que de dépanner un par un.
- Le README peut être fait par les retardataires en fin de séance ou à la maison.

**🛠️ Profil GitHub.** Exercice court et valorisant. Montrer un ou deux beaux profils (le sien, celui d'un ancien étudiant). Ceux qui n'ont pas fini terminent à la maison : ne pas dépasser les 10 minutes.

**🎤 Dépôt partagé.** Pendant ce bloc, faire bouger les étudiants pour qu'ils s'assoient par équipe. Annoncer le chef d'équipe de chaque équipe (celui dont le push a marché). Projeter le diagramme de séquence et annoncer : « Vous allez tous vous faire refuser votre push. C'est voulu. »

**👥 Dépôt commun.** Le goulot d'étranglement est l'**invitation** : tant qu'un membre n'a pas accepté, son push échoue avec `403`. Demander aux chefs d'inviter tout le monde **en premier**, et aux membres de surveiller [github.com/notifications](https://github.com/notifications). Faire taper `git config --global pull.rebase false` à tout le monde, même à ceux qui ne voient pas pourquoi.

**👥 Conflit volontaire : le moment fort de la séance.** Le faire vivre comme un jeu, au même signal pour toute la classe :
1. Projeter les consignes et un minuteur. Tout le monde fait `git pull`, modifie **la première ligne** du README avec **sa** proposition de nom d'équipe, `git add`, `git commit`, puis **lève la main** et **attend**.
2. Quand toutes les mains sont levées (ou après 4 minutes) : « Attention... 3, 2, 1, **push** ! ». Toute la classe pousse en même temps.
3. Laisser 30 secondes de chaos : un seul gagnant par équipe, les autres ont `rejected`, puis `CONFLICT` après le `git pull`. Demander : « Qui a eu un push accepté ? Qui a eu un conflit ? »
4. Projeter un conflit d'une équipe volontaire (ou celui du professeur sur `equipe-prof`), expliquer les trois marqueurs et les boutons de VS Code.
5. Consigne de résolution : **l'équipe choisit d'abord le nom à l'oral**, puis chacun écrit **exactement le même titre**. Ainsi, les derniers à pousser n'ont pas de nouveau conflit (Git fusionne sans conflit deux modifications identiques).
6. Débrief en une phrase : « Le conflit se règle en discutant, pas avec Git : c'est le C de CALMS. »

**Si on est en retard :** couper le profil GitHub (à faire à la maison) et faire le quiz 4.2 en début de séance 2. Ne jamais couper le conflit.

### Script de démonstration

**👀 Mettre un dépôt en ligne** (sur `~/demo/site-datacafe`)

1. Montrer d'abord que le dépôt local est propre :
   ```bash
   cd ~/demo/site-datacafe
   git status
   git log --oneline
   ```
2. Sur github.com : **+** → **New repository** → nom `site-datacafe`, description, **Public**. Montrer explicitement les trois cases *README*, *.gitignore*, *license* **non cochées**, et dire pourquoi (question Q5 du quiz). **Create repository**.
3. Montrer la page d'instructions de GitHub : on y retrouve presque mot pour mot les commandes qu'on va taper. Copier l'adresse HTTPS.
4. Dans le terminal :
   ```bash
   git remote add origin https://github.com/<pseudo-prof>/site-datacafe.git
   git remote -v
   git push -u origin main
   ```
5. Rafraîchir la page GitHub : fichiers en ligne, cliquer sur **commits** (l'historique du chapitre 3 est là), puis sur **Tags** : **vide**. Demander à la classe : « Où sont passés mes tags ? »
6. ```bash
   git push --tags
   ```
   Rafraîchir : `v1.0` à `v4.0` sont là.
7. Montrer en 30 secondes le README d'un dépôt connu (par exemple celui de Streamlit) pour expliquer le rôle de vitrine.

**Ce qui peut mal tourner en direct :**
- *Pas de demande d'identification* parce que les identifiants sont mémorisés : dire « la première fois, une fenêtre de connexion s'ouvre », et montrer la capture de la fenêtre ou l'encadré 🆘 du support.
- *`remote origin already exists`* (répétition de la veille) : `git remote set-url origin <url>`, et en profiter pour montrer la correction.
- *Réseau coupé :* basculer sur le partage de connexion ; à défaut, faire la démo sur `equipe-prof` déjà en ligne et montrer la page GitHub préparée.

**Mini-démo du rejet et du conflit** (facultative, dans le bloc 🎤 Dépôt partagé ou au moment du débrief du conflit), avec les deux clones `equipe-prof` et `equipe-prof-bis` ouverts dans deux terminaux côte à côte :

```bash
# Terminal 1 (equipe-prof)
echo "# Les Barista du Code ☕" > README.md
git commit -am "Proposition de nom d'équipe" && git push        # accepté
# Terminal 2 (equipe-prof-bis)
echo "# Team Espresso 🚀" > README.md
git commit -am "Proposition de nom d'équipe" && git push        # rejected (fetch first)
git pull                                                         # CONFLICT
```

Ouvrir `README.md` dans VS Code, montrer les marqueurs et les boutons **Accepter la modification actuelle / entrante / les deux**, résoudre, puis `git add README.md`, `git commit -m "Résolution du conflit sur le nom d'équipe"`, `git push`.

### Corrigés des exercices

**🛠️ Mettre votre site en ligne**

```bash
cd ~/cours-devops/site-datacafe
git status                                   # working tree clean
git remote add origin https://github.com/<pseudo>/site-datacafe.git
git remote -v                                # origin ... (fetch) / origin ... (push)
git push -u origin main
git push --tags
# création du README.md avec le contenu du support, puis :
git add README.md
git commit -m "Ajout du README"
git push
```

Résultat attendu : sur GitHub, `hello.html`, `style.css`, `README.md` (rendu sous la liste des fichiers), 5 commits, 4 tags. Valider en regardant l'écran ou en demandant l'URL du dépôt dans le tableau partagé.

Erreurs fréquentes :
- dépôt GitHub créé **avec** README : premier push `rejected (fetch first)`. Solution la plus simple pour un débutant : supprimer le dépôt GitHub (Settings → *Danger Zone* → *Delete this repository*) et le recréer vide. Pour les avancés : `git pull origin main --allow-unrelated-histories`, résoudre, puis `git push -u origin main` ;
- adresse copiée depuis un autre étudiant ou avec une faute : `Repository not found` → `git remote set-url origin <bonne-url>` ;
- terminal ouvert dans le mauvais dossier : `fatal: not a git repository` → `cd ~/cours-devops/site-datacafe` ;
- branche locale `master` au lieu de `main` (réglage `init.defaultBranch` oublié au chapitre 3) : `git branch -M main`, puis `git push -u origin main` ;
- README créé mais pas poussé : il est sur l'ordinateur et pas sur GitHub, faire `git status` puis `git push`.

**🛠️ Votre profil GitHub**

Dépôt public nommé **exactement** comme le pseudo (casse comprise), *Add a README file* coché, message *« You found a secret! »*, modification du README au crayon ✏️ et **Commit changes**. Valider sur `https://github.com/<pseudo>`. Erreur fréquente : une faute dans le nom du dépôt (pas de message secret, rien ne s'affiche sur le profil) : renommer le dépôt dans Settings. Défi 🔴 : générateurs de type « GitHub profile README generator », badges shields.io, statistiques *github-readme-stats*.

**👥 Le dépôt commun**

1. Le chef : dépôt public `equipe-datacafe` **avec** README, Settings → Collaborators → Add people (×3). Les membres acceptent l'invitation.
2. Chacun :
   ```bash
   cd ~/cours-devops
   git clone https://github.com/<pseudo-du-chef>/equipe-datacafe.git
   cd equipe-datacafe
   code .
   git config --global pull.rebase false
   ```
3. Carte de membre `membres/<prenom>.md`, puis `git add`, `git commit -m "Ajout de la carte de membre de Prénom"`, `git push`.
4. Le premier passe, les autres : `rejected (fetch first)` → `git pull` (VS Code ouvre le message `Merge branch 'main' of ...` : fermer l'onglet) → `git push`.
5. Un dernier `git pull` pour tous : 4 fichiers dans `membres/`.

Critère de validation : sur GitHub, le dossier `membres` contient 4 fichiers, et `git log --oneline --graph` montre des commits de fusion.

Erreurs fréquentes :
- `remote: Permission to ... denied` / `403` : invitation non acceptée, ou le chef a invité un mauvais pseudo ;
- dossier `membres` vide non commité : Git ne suit pas les dossiers vides, il faut le fichier dedans ;
- fichier enregistré hors du dépôt (VS Code ouvert sur `cours-devops` au lieu de `equipe-datacafe`) : `git status` ne voit rien ;
- clone fait **à l'intérieur** de `site-datacafe` (dépôt dans un dépôt) : supprimer et recloner depuis `~/cours-devops` ;
- `fatal: Need to specify how to reconcile divergent branches` : le réglage `pull.rebase false` a été oublié. Le taper, puis refaire `git pull` ;
- Git ouvre **Vim** pour le message de fusion (réglage `core.editor` absent) : taper `:wq` puis Entrée.

**👥 Le conflit volontaire**

Après le `git pull` conflictuel, `README.md` contient les marqueurs. Résolution attendue : un seul titre, plus aucun marqueur, puis :

```bash
git add README.md
git commit -m "Résolution du conflit sur le nom d'équipe"
git push
```

Critères : README sur GitHub avec un seul nom, `git pull` → `Already up to date.` partout, et dans `git log --oneline --graph` une fusion visible.

Erreurs fréquentes :
- **marqueurs restés dans le fichier** (`<<<<<<<` visibles sur GitHub) : corriger le fichier, nouveau commit, push ;
- conflits en cascade : un membre résout et pousse, un autre a résolu autrement, son push est refusé, nouveau `pull`, nouveau conflit. C'est normal : rappeler de **se mettre d'accord à l'oral** et d'écrire exactement le même titre ;
- étudiant qui a fait `git push` sans avoir commité : rien ne part (`Everything up-to-date`), il doit faire `git add` et `git commit` d'abord ;
- étudiant qui « perd » son commit en paniquant : `git status` indique `You have unmerged paths` ; en dernier recours `git merge --abort` remet l'état d'avant le `pull`, puis on recommence calmement.

### Points d'animation

**💬 Tour de table.** Profiter des réponses à la question 2 pour faire raconter un conflit par un étudiant. Faire faire un `git pull` à tout le monde dans `equipe-datacafe` dès l'arrivée (règle d'or en action).

**🎤 Branches.** Insister sur l'idée que `main` doit **toujours fonctionner**. L'exemple de M. Robert parle bien aux étudiants de MBA : le client ne doit jamais voir un site cassé. Bien faire noter la règle « on se place sur la branche qui **reçoit** ».

**🛠️ Diplômes.** Les débutants recopient les commandes du support : c'est attendu. Aux rapides, donner le 🟡 (`ajout-contact`) puis leur demander d'expliquer `git log --oneline --graph --all` à leur voisin.

**🎤 Pull Requests.** Faire la mini-démo de PR sur `equipe-prof` (2 minutes) : bandeau **Compare & pull request**, onglet **Files changed**, commentaire, **Approve** par le deuxième compte ou un étudiant, **Merge**, **Delete branch**. Le fork se dit en une phrase ; ne pas le faire pratiquer.

**👥 Recettes : la course aux 4 PR.**
- Annonce : « Première équipe avec **4 PR fusionnées, chacune approuvée par un coéquipier avec au moins un commentaire**, gagne 3 points. » Le chef d'équipe lève la main quand c'est fait ; vérifier dans l'onglet **Pull requests → Closed** (4 PR violettes *Merged*, chacune avec une *review* approuvée).
- Organiser la relecture en **cercle** : chacun relit la PR de son voisin de gauche, pour que personne ne soit oublié.
- Débutants : les associer au référent Git de l'équipe qui lit les étapes à voix haute.
- Rapides : leur demander de laisser une vraie suggestion (bouton *Add a suggestion* dans **Files changed**) que l'auteur accepte avant la fusion.

**🎤 Issues et Kanban.** Relier au chapitre 1 (Agilité, Kanban, étape 📋 Plan). Montrer un tableau Projects déjà rempli sur `equipe-prof` pour gagner du temps.

**👥 Sprint.** Le chef d'équipe joue le **Product Owner**. Le professeur peut jouer le « client » qui passe dans les équipes et demande « où en est l'issue n° 2 ? », les étudiants doivent répondre en montrant le tableau. Si l'interface Projects pose problème, accepter un sprint sans tableau (issues + `Closes #` seulement) : l'essentiel est la fermeture automatique.

**🛠️ Zéro commande.** Montre aux étudiants les moins à l'aise avec le terminal qu'ils ont une alternative. Les plus avancés font le défi github.dev.

**👥 Release.** Moment de clôture : chaque chef d'équipe projette ou montre sa page de release. Proclamer l'équipe gagnante du chapitre.

**Si on est en retard :** réduire le sprint à 2 issues par équipe, faire « Zéro commande » à la maison, garder impérativement la course aux PR (c'est le GitHub Flow du chapitre 5 et du projet) et la release (2 minutes suffisent au chef).

### Script de démonstration

**👀 Une branche, de la création à la fusion** (sur `~/demo/site-datacafe`, après la séance 1 il est déjà relié à GitHub)

```bash
cd ~/demo/site-datacafe
git pull
git branch                  # * main
git switch -c diplomes
git branch                  # * diplomes
```

1. Ajouter dans `hello.html`, à la fin de la description :
   ```html
   <h1>Mes diplômes</h1>
   <p>Master ..., École ...</p>
   ```
   Ouvrir la page avec Live Server : la section est visible.
2. ```bash
   git add hello.html
   git commit -m "Ajout de la section diplômes"
   git switch main
   ```
   Rafraîchir la page dans le navigateur : **la section a disparu**. Demander « Est-ce que j'ai perdu mon travail ? ». Puis `git switch diplomes` : elle revient. Montrer le nom de branche en bas à gauche de VS Code, qui change.
3. ```bash
   git switch main
   git merge diplomes
   git log --oneline --graph --all
   git branch -d diplomes
   git tag -a v5.0 -m "Version 5 : ajout des diplômes"
   git push
   git push --tags
   ```
   Faire remarquer le message `Fast-forward` : `main` n'avait pas bougé, Git a simplement avancé l'étiquette `main`. Pour avoir un vrai embranchement dans le graphe, faire un petit commit sur `main` avant le merge (optionnel).

**Ce qui peut mal tourner :**
- `git switch main` refusé (`Your local changes would be overwritten`) : on a oublié de commiter. Commiter, puis recommencer. Bonne occasion de le dire à la classe.
- `git branch -d` refusé (`not fully merged`) : on a oublié le merge, ou on est sur la mauvaise branche.

**Mini-démo PR** (dans le bloc 🎤 Pull Requests), sur `equipe-prof` avec la branche `ajout-recette-prof` préparée : **Compare & pull request** → titre, description → **Create pull request** → onglet **Files changed** → depuis le second compte (ou par un étudiant) : commentaire, **Review changes** → **Approve** → **Submit review** → **Merge pull request** → **Confirm merge** → **Delete branch**. Puis en local :

```bash
git switch main
git pull
git log --oneline --graph --all
```

**Mini-démo Issues et Kanban :** sur `equipe-prof`, créer une issue « Ajouter une page `horaires.md` », montrer l'**Assignees**, le tableau **Projects** (*Board*), et une PR dont la description contient `Closes #1` : à la fusion, l'issue se ferme et la carte passe dans **Done**.

**Mini-démo interfaces graphiques :** `Ctrl + Maj + G` dans VS Code, le **+**, **Valider**, **Synchroniser**, le nom de branche en bas à gauche, l'extension **Git Graph**. Puis, sur la page GitHub de `equipe-prof`, appuyer sur `.` : github.dev s'ouvre.

### Réponses du quiz

**Quiz · Branches et Pull Requests**

| Question | Réponse | Explication | Piège typique |
|---|---|---|---|
| Q1. Créer et se placer | **B** `git switch -c contact` | `-c` = *create*. Équivalent ancien : `git checkout -b contact`. | A crée la branche mais **ne s'y place pas**. |
| Q2. Sur quelle branche pour `git merge contact` ? | Sur **`main`**, la branche qui **reçoit** les modifications. | On « fait entrer » `contact` dans la branche où l'on se trouve. | Se placer sur `contact` (on fusionnerait `main` dans `contact`). |
| Q3. Pull Request | **B** | Demander la relecture et la fusion d'une branche dans une autre. | Confondre avec `git pull` (récupérer). Le nom est trompeur : c'est une « demande de fusion ». |
| Q4. Pourquoi pas sur `main` ? | Parce que `main` doit toujours contenir une version qui fonctionne. On teste les nouveautés dans des branches et on ne fusionne qu'après vérification. | | Répondre « c'est interdit par Git » : Git le permet, c'est une **règle d'équipe**. |
| Q5. Clone ou fork | Un **clone** copie un dépôt sur **votre ordinateur**. Un **fork** copie le dépôt de quelqu'un d'autre dans **votre compte GitHub**. | On clone souvent son fork ensuite pour y travailler. | Penser que fork et clone sont synonymes. |

### Corrigés des exercices

**🛠️ Vos diplômes dans une branche**

```bash
cd ~/cours-devops/site-datacafe
git pull
git switch -c diplomes
# ajout de <h1>Mes diplômes</h1><p>...</p> dans hello.html
git add hello.html
git commit -m "Ajout de la section diplômes"
git switch main            # la section disparaît
git switch diplomes        # elle revient
git switch main
git merge diplomes
git log --oneline --graph --all
git branch -d diplomes
git tag -a v5.0 -m "Version 5 : ajout des diplômes"
git push
git push --tags
```

Validation : `git branch` → `* main` seulement ; onglet **Tags** sur GitHub → `v5.0`. 🟡 : même chose avec `ajout-contact` (sans tag obligatoire).

Erreurs fréquentes : oubli du `git push --tags` ; `merge` lancé depuis la branche `diplomes` (`Already up to date.`, rien ne se passe sur `main`) ; nom de branche avec espace ou accent (`diplômes`) qui fonctionne localement mais pose problème ailleurs : le renommer avec `git branch -m diplomes`.

**👥 Recettes par Pull Requests**

Pour chaque membre :

```bash
cd ~/cours-devops/equipe-datacafe
git switch main
git pull
git switch -c ajout-recette-prenom
# création de recettes/prenom.md
git add recettes/prenom.md
git commit -m "Ajout de la recette de Prénom"
git push -u origin ajout-recette-prenom
```

Puis sur GitHub : **Compare & pull request** → **Create pull request** ; relecture du voisin (**Files changed**, commentaire, **Review changes** → **Approve** → **Submit review**) ; l'auteur : **Merge pull request** → **Confirm merge** → **Delete branch**. Enfin `git switch main`, `git pull`, `git log --oneline --graph --all`.

Résultat attendu : 4 fichiers dans `recettes/`, 4 PR *Merged* dans **Pull requests → Closed**, le graphe montre les 4 fusions (`Merge pull request #1 from ...`).

Erreurs fréquentes :
- branche créée sans avoir fait `git pull` sur `main` : pas grave ici (fichiers différents), mais le rappeler ;
- commit fait sur `main` au lieu de la branche (oubli du `switch -c`) : `git switch -c ajout-recette-prenom` **emporte** le commit avec lui ; puis remettre `main` d'aplomb avec `git switch main` et `git reset --hard origin/main` (à faire **avec** l'étudiant, commande destructrice) ;
- bandeau **Compare & pull request** absent : passer par l'onglet **Pull requests** → **New pull request** → *compare* : la branche ;
- « Approve » grisé : on ne peut pas approuver sa propre PR, il faut un coéquipier ;
- après la fusion, l'étudiant reste sur sa branche locale et ne voit pas les recettes des autres : `git switch main` puis `git pull`. Pour nettoyer la branche locale : `git branch -d ajout-recette-prenom`.

**👥 Le sprint de l'équipe**

- 4 issues créées par le chef, ajoutées à un Project *Board* (onglet *Projects* → *Link a project* → *New project* → *Board*). Si l'interface a changé, créer le projet depuis le profil (**Your projects** → **New project** → **Board**), puis l'ajouter au dépôt.
- Chaque membre : s'assigne l'issue (**Assignees**), la déplace dans **In Progress**, `git switch main`, `git pull`, `git switch -c <nom-court>`, crée le fichier (`horaires.md`, `contact.md`, `menu.md` ou complète le README), commit, `git push -u origin <branche>`, PR avec `Closes #<numéro>` dans la description.
- Après relecture et fusion : issues fermées automatiquement, cartes dans **Done** (les flux automatiques *Item closed* et *Pull request merged* du projet sont actifs par défaut).

Erreurs fréquentes : `Closes #3` écrit dans le **titre** de la PR au lieu de sa description (le mot-clé fonctionne dans la description ou dans un message de commit, pas dans le titre) ; numéro d'issue erroné (on ferme l'issue d'un autre) ; la tâche « Compléter le README » entre en conflit avec une autre PR qui modifie le README : c'est l'occasion de résoudre un conflit **dans l'interface GitHub** (bouton **Resolve conflicts**) ou en local (`git pull origin main` dans la branche, résolution, push).

**🛠️ Zéro commande**

Nom de branche en bas à gauche → **Créer une branche** → `ajout-citation-prenom` ; modification de la carte ; panneau Contrôle de code source : **+**, message, **Valider** ; **Publier la branche** ; PR, approbation, fusion sur GitHub ; retour sur `main` (clic en bas à gauche) et **Synchroniser**. Validation : la citation est sur `main` sur GitHub et en local. Erreur fréquente : VS Code demande « Voulez-vous indexer automatiquement toutes les modifications ? » : répondre **Oui** est acceptable ici. Défi 🔴 : touche `.` sur la page du dépôt, modification dans github.dev, commit depuis le panneau Contrôle de code source du navigateur (choisir de créer une branche et une PR, ou commiter sur `main` si l'équipe l'accepte).

**👥 Publier la v1.0 de l'équipe**

Toutes les PR fusionnées, `git switch main`, `git pull` pour tous. Le chef : **Releases** → **Create a new release** → **Choose a tag** → `v1.0` → **Create new tag**, titre « Version 1.0 de l'équipe », description (liste du contenu : membres, recettes, pages horaires/contact/menu), **Publish release**. Chacun : `git pull --tags`, `git tag` → `v1.0`.

Défi 🔴 (README d'équipe) attendu : présentation, liste des membres avec liens `https://github.com/<pseudo>`, arborescence (`membres/`, `recettes/`, pages), règles de contribution. Idéalement, le README passe lui-même par une PR.

Erreur fréquente : release créée alors qu'une PR n'était pas fusionnée : le tag pointe sur une version incomplète. Pour corriger : supprimer la release et le tag sur GitHub, fusionner, recréer.

## Pièges fréquents et dépannage

| Symptôme | Cause | Solution |
|---|---|---|
| Le terminal demande *Username* / *Password* et refuse le mot de passe | GitHub n'accepte plus le mot de passe du compte depuis 2021 | Jeton d'accès personnel (classic, case **repo**, 90 jours) collé comme mot de passe (encadré 🆘 du support). Ou bouton « Se connecter avec GitHub » de VS Code |
| `Authentication failed` alors que le jeton est bon | Anciens identifiants mémorisés | Windows : **Gestionnaire d'identification** → *Informations d'identification Windows* → supprimer `git:https://github.com`. Mac : **Trousseau d'accès** → chercher `github.com` → supprimer. Puis refaire `git push` |
| Le jeton est redemandé à chaque push (Linux) | Pas de gestionnaire d'identifiants | `git config --global credential.helper 'cache --timeout=36000'` (mémorise 10 h en mémoire, sans l'écrire dans un fichier) |
| `remote: Permission to ... denied` / `403` | Invitation au dépôt d'équipe non acceptée, ou push vers le dépôt d'un autre | Accepter l'invitation sur github.com/notifications ; vérifier `git remote -v` |
| `Repository not found` | Faute dans l'adresse, dépôt privé sans accès, ou mauvais compte connecté | `git remote -v`, `git remote set-url origin <url>` |
| `error: remote origin already exists.` | `git remote add` lancé deux fois | `git remote set-url origin <url>` |
| `! [rejected] main -> main (fetch first)` | Quelqu'un a poussé avant | `git pull` puis `git push` |
| `fatal: Need to specify how to reconcile divergent branches` | `pull.rebase` non configuré | `git config --global pull.rebase false`, puis `git pull` |
| Premier push de `site-datacafe` refusé | Dépôt GitHub créé avec un README | Supprimer et recréer le dépôt vide (ou `git pull origin main --allow-unrelated-histories`) |
| Vim s'ouvre au `git pull` | `core.editor` non configuré | `:wq` puis Entrée ; puis `git config --global core.editor "code --wait"` |
| Marqueurs `<<<<<<<` visibles sur GitHub | Conflit commité sans être nettoyé | Supprimer les marqueurs, commit, push |
| `error: src refspec main does not match any` | Branche locale nommée `master`, ou aucun commit | `git branch -M main`, puis `git push -u origin main` |
| Clone impossible depuis la salle | Réseau de l'école qui filtre | Partage de connexion du téléphone ; vérifier la veille |
| Impossible de créer un dépôt / de pousser avec un compte neuf | E-mail non validé, ou double authentification exigée | Renvoyer l'e-mail de validation (Settings → Emails) ; activer la 2FA avec une application |
| Les commits n'apparaissent pas avec la photo de l'étudiant sur GitHub | E-mail de `git config` différent de celui du compte | Ajouter l'e-mail dans Settings → Emails, ou corriger `git config --global user.email` pour les prochains commits |

### Plan B si l'authentification GitHub échoue en classe

Ne pas laisser un étudiant bloqué plus de 10 minutes : il doit pouvoir vivre le travail d'équipe.

1. **Essayer dans l'ordre :** fenêtre « Se connecter avec GitHub » de VS Code (ou Git Credential Manager sous Windows) → jeton d'accès personnel → suppression des anciens identifiants mémorisés.
2. **Contournement par le site web** (aucune authentification Git nécessaire) : pour `site-datacafe`, **Add file → Upload files** pour déposer `hello.html` et `style.css` (sans historique, mais le dépôt existe) ; pour le dépôt d'équipe, **Add file → Create new file** (`membres/prenom.md`, `recettes/prenom.md`), en choisissant *Create a new branch ... and start a pull request* au moment du commit. Les PR, issues, Kanban et release se font entièrement sur le site.
3. **github.dev** (touche `.`) : édition et commit depuis le navigateur, avec création de branche.
4. **Binôme** : l'étudiant observe et dicte sur l'ordinateur d'un coéquipier pour les exercices solo, mais fait ses propres contributions d'équipe par le site web (les commits restent ainsi à son nom).
5. Le problème est réglé **à la maison** avant la séance suivante (indiqué dans « 🏠 Avant la séance 2 ») ; le professeur vérifie au début de la séance 2, car le chapitre 5 suppose que `git push` fonctionne.

## Pour aller plus loin

- **GitHub Skills** (skills.github.com) : parcours interactifs gratuits (Introduction to GitHub, Review pull requests, Resolve merge conflicts).
- **Learn Git Branching** (learngitbranching.js.org) : visualisation animée des branches et des fusions, excellente pour les étudiants avancés.
- **Pro Git**, chapitres 3 (branches) et 6 (GitHub), gratuit en français sur git-scm.com.
- Questions d'approfondissement pour les avancés :
  - Quelle est la différence entre `git pull` et `git fetch` ? Que fait `git pull --rebase` (et pourquoi a-t-on choisi `pull.rebase false` pour débuter) ?
  - Qu'est-ce qu'une **protection de branche** (Settings → Branches) ? Configurez `main` pour exiger une PR approuvée avant toute fusion.
  - Qu'est-ce qu'un fichier `CODEOWNERS` ? Et un modèle de PR (`.github/pull_request_template.md`) ?
  - Faites une première contribution open source : fork d'un dépôt d'exercice (par exemple *first-contributions* sur GitHub), branche, PR vers le dépôt d'origine.
  - Découvrez **GitHub Actions** : une action qui se déclenche à chaque push (préparation des étapes 🧪 Test et 🚀 Deploy de la boucle DevOps).
